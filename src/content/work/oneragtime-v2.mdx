## Where it started

OneRagtime is a venture platform. Investors put money into startups through funds and single-deal vehicles, and a back office runs the rest: onboarding, compliance checks, signatures, valuations, quarterly reports. About €97M has gone through it since 2018.

When I joined as an intern in 2023, the code was already five years old: a Django app on MySQL and AWS, with an investor app half on an older Vue setup. It worked. It was also getting slower to change every month, and it cost a lot to host for the size of team we had.

By late 2025 I'd been one of two engineers for a while, and I made the case for a rewrite. I wrote the plan, led it, and wrote most of the code: the new data model, the backend, the frontend base and design system, the checks that the numbers still matched, and the hosting move. My colleague built features on top as we went. Since September 2026 I've been the only engineer, and I'm now onboarding the next one.

## How we did it without a launch day

The thing I was most scared of was a launch weekend: switch everything over on a Friday and find out on Monday that someone's investment shows the wrong amount. So the rule was that there would never be a big switch.

<StranglerFig />

In order, that meant:

1. **New frontends first, on the old API.** People got the new admin and investor apps months before any backend changed, and I learned what every screen really needed by rebuilding it.
2. **A new backend on the same tables.** The new Django project points at the existing database and doesn't own the schema (`managed = False`). Old and new code read and write the same rows, so there's nothing to sync.
3. **Check the numbers before switching.** A small harness ran valuations, KPIs and investor positions through both systems and listed every difference.
4. **Switch one app at a time.** The admin app first, since its users were the internal team and would tell me fast if something was off. The investor app about ten days later. Going back would have meant pointing the frontend at the old API again.
5. **Then move house.** MySQL to Postgres, AWS to Railway and Vercel, and the old servers switched off.

## Bits that were harder than they looked

**Sharing one schema between two codebases.** Every schema change had to keep the old app working too. I put clean models over the awkward legacy tables where I could, and changed the tables themselves slowly. By the end there were 101 tables instead of 154, and 14 migration files instead of 44.

**Agreeing on what "the same numbers" means.** The harness got to 111 of 112 KPIs matching. The last one was a change we made on purpose and wrote down before switching. I also replaced the valuation recalculation, which used to take minutes per startup, with a batch version: about 0.3 s per startup, and around 7 s for the whole portfolio.

**The database move.** MySQL to Postgres was a separate step, not mixed in with any refactoring. I wrote a migration script that could be run again safely, practised it on copies of production until it was dull, and ran it for real once.

**Doing it with two people.** We used coding agents for a lot of the typing. To keep that safe there were written specs before code, around 4,000 tests running on every pull request, a preview environment for each pull request with a copy of production data, and an automated review before anything merged.

## Numbers

- Hosting costs down about **95%** after the old AWS setup was switched off.
- **111 of 112** KPIs identical before the switch. The other one was intentional.
- About **450** active investors moved over. They had to log in again once.
- About **4,000** tests, and portfolio revaluation in seconds instead of minutes.

## Stack

Django, Django REST Framework and GraphQL on PostgreSQL, Celery for background jobs, and Vue 3 with Vite and Pinia for the apps. Railway runs the backend, Vercel runs the frontends, and GitHub Actions runs the tests and preview environments.
