## Why

On a small team the engineer ends up being the search box. "Have we talked to anyone at this company?" "What did this startup report last quarter?" "Who do we know at that fund?" None of these are hard, but each one used to be a message to me, and I'd lose ten minutes getting back into whatever I was doing.

The answers were already in the platform behind an internal GraphQL API. What the team didn't have was a way to ask in plain English. MCP (Model Context Protocol) lets an assistant like Claude call tools you write, so I wrote some.

## What it does

The server gives Claude 19 small, read-only tools: search investors, get a startup, list our contacts at a company, summarise a portfolio, and so on. Someone on the team adds it to Claude once and then just asks. Today all 12 people on the business team use it, mostly for meeting prep and quick lookups.

Each tool turns into a read-only query against the platform API, using a service token the server refreshes on its own. Nothing can write, so the worst a bad question can do is give a wrong answer, and a person reads the answer before acting on it.

## Things the model got wrong, and what I did about it

**It guesses field names.** Ask about an investor's company and the model will happily ask for `companyName`, `company`, `organisation` or `org_name`. At first that meant a failed call, an apology from the model and another guess. Now the server keeps a short list of common guesses per resource, maps them to the real field, and says which fields exist when it can't.

**It asks for too much.** A raw investor record has dozens of fields. Sending all of them back for "list our fintech investors" fills the context window with junk and makes the answer worse. Every tool takes an optional list of fields and returns only those. If the model doesn't ask for specific fields, it gets a small default set.

**It doesn't know when to stop.** Read-only can still mean "read the whole table". Every query has a 5,000-row cap and a 20-second timeout, enforced on the server. When a limit hits, the model gets a plain message ("too many rows, add a filter") and usually just narrows the question.

All of these checks live in the server, not in the prompt, so they still apply when the model ignores its instructions.

## Stack

TypeScript on Node with Express 5 and the official MCP SDK (Streamable HTTP), talking to the platform's GraphQL API. It's packaged with Docker and runs on Railway next to the rest of the platform.
