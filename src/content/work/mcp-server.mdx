## Why

On a small team the engineer ends up being the search box. "Have we talked to anyone at this company?", "What did this startup report last quarter?", "Who do we know at that fund?" None of these are hard, but each one used to be a message to me, and I'd lose ten minutes getting back into whatever I was doing.

The answers were already in the platform. What the team didn't have was a way to ask in plain English. MCP (Model Context Protocol) lets an assistant like Claude call tools you write, so I wrote some. The team uses it for meeting prep, portfolio holdings and valuations, drafting investor emails from everything we already know about them, and a scheduled morning brief.

## Version one: a tool per question

The first version, in 2025, had 17 fixed tools over the old REST API: list investors, get an investor, get a startup's reports, and so on. Each took an optional list of fields, so the model could ask for three columns instead of a record with dozens. It also kept a small map of the field names the model kept guessing (`total_amount_raised`, `raised_amount`, `current_amount`) and pointed them at the real one.

It worked, but it had a cost I didn't like. Every time the backend grew, the MCP server fell behind. A new field meant a new release, and a question nobody had planned for meant a new tool.

## Version two: GraphQL, and fewer inputs

When the new backend shipped with a GraphQL API, I replaced the fixed tools with two:

- `core_graphql_query` takes a query and, optionally, its variables. Nothing else.
- `core_graphql_schema` takes nothing and returns a short guide: the entry points, the filters, and example queries for the common questions.

That fixed both problems at once. Anything the backend adds to its GraphQL schema can be queried the same day, with no change to the MCP server. And picking fields is now just how GraphQL works, so the field lists and guessed-name maps went away. The only thing I keep up by hand is the guide, and it's a list of examples, not a contract.

I also learned that agents do better with fewer, simpler tools. Two inputs are hard to get wrong. Seventeen tools with five optional parameters each gave the model a lot of ways to pick slightly the wrong one.

Alongside the two GraphQL tools sit three helpers: the semantic search described below, and two readers that pull the text out of a web page or a PDF.

## Limits live in the backend, not the prompt

Read-only isn't the same as harmless: a vague question can still ask for every row in a table. So the backend enforces the limits for every query, whatever the model was told:

- read-only, through a service account that can only see what it was built to see
- at most 5,000 rows
- a 20-second database timeout, set per request

When a limit is hit, the model gets a plain message telling it to narrow the question, which is what a person would do too.

## Search, and when not to use it

The server also has a semantic search over email, internal notes and decks. It's good at "what did we discuss with this fund?" and bad at "have we ever emailed this person?", because it always returns its closest matches, even when nothing really matches. When I checked a real batch of "have we contacted these people" questions answered that way, 43% of the "no" answers were wrong.

The fix had two parts. I added an exact email-thread query to GraphQL, so a "no" from it can be trusted. And I moved the warning from a parameter description, where the model read it too late, into the first lines of the tool's description.

## Stack

TypeScript on Node with Express 5 and the official MCP SDK (Streamable HTTP), in front of the Django backend's GraphQL API. It's packaged with Docker, lives in the same repository as the backend, and runs on Railway next to the rest of the platform.
