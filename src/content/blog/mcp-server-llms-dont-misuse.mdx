For a while the most common thing I did at work wasn't writing features. It was answering questions. "Which investors have we talked to about this company?" "What did this startup report last quarter?" "Who do we know at that fund?" Each takes thirty seconds to answer and longer than that to get back into whatever I was doing.

So I built an MCP server and let Claude answer them. MCP (Model Context Protocol) lets an assistant call tools you define. Now the whole business team, 12 people, asks their assistant directly, mostly when preparing for meetings. This is what I ran into building it.

## Small tools, all read-only

The easy version would be one tool, `run_query(sql)`, plus a system prompt asking the model to be careful. I didn't want to rely on the model being careful, so the server only offers 19 small tools, like `search_investors`, `get_startup`, `list_contacts_at_company` and `portfolio_summary`. Each has a typed input and does one thing.

```ts
server.registerTool(
  "search_investors",
  {
    description: "Find investors by name, company or tag. Read-only.",
    inputSchema: {
      query: z.string().min(2),
      fields: z.array(z.string()).optional(), // see "asking for too much" below
      limit: z.number().int().max(200).default(25),
    },
  },
  async ({ query, fields, limit }) => runReadOnly("investors", { query, fields, limit }),
);
```

None of the tools can write anything. The worst a bad call can do is return a wrong answer, and a person reads the answer before doing anything with it. The model also picks the right tool more often when the choices are specific than when one tool does everything.

## Problem 1: asking for too much

An investor record has dozens of fields: addresses, flags, timestamps, related records. If you send all of that back for "who are our fintech investors?", you fill the model's context with things it won't use, and the answer gets worse.

Every tool takes an optional list of fields and returns only those:

```ts
function project<T extends Record<string, unknown>>(rows: T[], fields?: string[]) {
  if (!fields?.length) return rows.map(defaultView);       // a small default set
  return rows.map((r) => Object.fromEntries(fields.filter((f) => f in r).map((f) => [f, r[f]])));
}
```

If the model doesn't ask for anything specific, it gets a short default set instead of the full record. I did it to save tokens, but it seems to help the answers too, since there's less for the model to misread.

## Problem 2: guessing field names

Ask about someone's company and in one afternoon you'll see the model ask for `companyName`, `company`, `organisation` and `org_name`. Rejecting the call meant an apology from the model, another guess, and a few wasted round trips.

So the server keeps a short list of common guesses for each resource and maps them to the real names:

```ts
const SYNONYMS: Record<string, string> = {
  companyName: "company", organisation: "company", org_name: "company",
  email_address: "email", fullName: "name",
};

function normalizeFields(fields: string[], allowed: Set<string>) {
  const mapped = fields.map((f) => SYNONYMS[f] ?? f);
  return { ok: mapped.filter((f) => allowed.has(f)), unknown: mapped.filter((f) => !allowed.has(f)) };
}
```

Field names it still doesn't recognise aren't an error either. The response just includes a note listing the fields that do exist, and the model usually gets it right on the next try.

## Problem 3: not knowing when to stop

Read-only isn't the same as harmless. A vague question can still ask for every row in a table. So every query, whichever tool it came through, runs with the same limits:

- at most 5,000 rows
- at most 20 seconds
- its own service account, with a short-lived token the server refreshes itself, so it can only see what it was built to see

When a limit is hit, the model gets a plain message like "too many rows, add a filter" and narrows the question, which is what a person would do too.

## What people actually use it for

Nothing exotic. Notes before an investor meeting, "have we talked to anyone at this company?", the latest numbers for a startup before a call, and who we know at a particular firm. They're the same questions that used to come to me.

## What's missing

I log which tools run and how long they take. What I'd really like to see is the questions people asked that the server couldn't answer, because that's the list of tools to build next. The synonym list is also still maintained by hand, and should really be built from the field names the model asks for that don't exist.
