In 2022 I spent a lot of evenings on TON smart-contract contests. That's how I ended up sending three bug reports about the FunC compiler over about 15 months. One was my fault, one paid 1,000 TON, and one paid 250 TON and changed a compiler default. Here's how each went.

Quick background if you haven't used it: FunC is the language TON smart contracts are written in. It looks a bit like C, compiles to Fift assembly, and runs on the TON Virtual Machine, which is a stack machine. Your variables are really names for slots on a stack, and the compiler's job is to shuffle those slots so the code does what you wrote. When it shuffles wrong, nothing crashes. A variable just ends up holding the wrong value, which in a smart contract can mean real money.

## Report 1: it was me (September 2022)

I was debugging a contest solution and saw two variables swap values between lines for no reason I could see. The contest's own judge seemed to have hit the same thing, so I was fairly sure it wasn't just me.

I cut the contract down to about ten lines, wrote a comment on each line saying what should happen, and sent it to the TON bug bounty bot with my output attached.

A couple of hours later they asked which compiler version I had, and which `Asm.fif`. They thought it was a known problem with empty `IF` blocks that had been fixed in May. I'd built my tools from source in early April.

I ran `toncli update_libs`, ran the script again, and got the right output. Report closed. Their sign-off was "Maybe next time we will together fix serious vulnerability", which was kind of them.

So, first thing I check now before blaming any compiler, framework or library: am I actually on the current version?

## Report 2: the loop that didn't run (December 2022)

Three months later, during another contest, a loop stopped looping. This is the whole proof of concept I sent, comments included:

```c
() recv_internal() impure { }

() my_fn() method_id {
  int multiplier = 1;           ;; initialize variable
  while (multiplier == 1) {     ;; this condition is met, but compiler thinks not
    ~dump(999);                 ;; dump statement not executed
    multiplier *= 2;            ;; ensure this doesn't run forever
  }
  ~dump(multiplier);            ;; still unchanged (multiplier still 1)
  ;; PS: using an if instead renders the correct output
}
```

`multiplier` starts at 1, so `multiplier == 1` is true and the body should run once: print `999`, double `multiplier` to 2, then exit. Instead the body never ran, and `multiplier` was still 1 afterwards. The same check written as an `if` worked fine.

My guess is the compiler used what it knew about `multiplier`'s starting value to simplify the loop condition and got the `while` case wrong. I never looked at the fix, though, so that part is only a guess.

The timeline I do know:

- 28 Dec, 10:23: report sent
- 28 Dec, 14:00: "Hi, we are checking it"
- 29 Dec: fixed in the testnet branch, and a bounty of **1,000 TON** (about $2,400 at the time)

Less than a day and a half. The reason it was taken seriously is that skipped code in a contract fails silently. A skipped loop could be a skipped balance update or a skipped check, with no error anywhere.

## Report 3: argument order (January 2024)

The last one was about the order arguments get evaluated in when you call an `asm` function. FunC lets you write functions directly in assembly, and their parameters can be listed in whatever order the assembly wants them on the stack. The compiler used to evaluate the arguments in that stack order, not left to right as you wrote them. Most of the time you'd never notice. When the arguments have side effects, like reading from the same slice twice, the order is everything:

```c
;; a made-up example, not the code I reported
(int, int) read_pair(slice cs) {
  return pack(cs~load_uint(8), cs~load_uint(8));
}
```

If `pack` is an `asm` function whose stack order is reversed, the two reads can happen in the opposite order and your two fields come back swapped. There was already an opt-in fix, `#pragma compute-asm-ltr`, but you only turn on things you know about.

This one took a while. They confirmed it after three weeks, then said they needed more time, then that they were preparing a bigger FunC update that would cover it. I followed up about once a month.

After almost six months I got the full answer. The team already knew about the behaviour and had decided it wasn't serious enough to change. My report showed a case where it changed things "drastically and in unexpected way", and that was enough: `compute-asm-ltr` became **the default in FunC 0.5.0**, along with some other changes. The bounty was 250 TON, adjusted for the TON price when I reported it (I'd asked about that).

It's the smaller of the two payouts, and the one I'm happiest about, because anyone writing FunC now gets the safer behaviour without ever reading my report.

## What I took from it

Looking at the three side by side, the reports that worked had a few things in common. They were tiny, about ten lines. Every line had a comment saying what should happen. Report 2 had the `if` version that worked, which pointed straight at the problem. And when it was slow, I kept following up politely instead of giving up.

What I'd do differently is mostly about report 3. I described the behaviour and left the impact implied, and the team already knew the behaviour. If I'd opened with a realistic contract whose fields come back swapped, I think it would have moved faster than six months. I also should have offered my repro scripts as test cases to the compiler repo, not just as attachments in a chat.
