Between late 2025 and autumn 2026 I led the rewrite of the platform I work on: the system investors use to put money into startups, and that the back office uses for onboarding, signatures, valuations and quarterly reports. For most of it we were two engineers. I proposed it, planned it and wrote most of the code.

The one thing I didn't want was a launch day: build the new system for a year, switch everything over on a Friday, and spend Monday finding out which investor's numbers are wrong. This post is about how we avoided that. It's the strangler-fig pattern, nothing new, but most write-ups I'd read stop before the boring details, so here are ours.

## One database, two apps

Most rewrites start a new system with a new database, and then need a migration, a sync job, and a weekend of hoping the two agree. We never had a second database.

The new backend is a fresh Django project pointed at the same tables as the old app. Django lets a model describe a table it doesn't own:

```python
class Investment(models.Model):
    investor = models.ForeignKey("people.Investor", on_delete=models.PROTECT, db_column="investor_id")
    amount = models.DecimalField(max_digits=14, decimal_places=2)
    signed_at = models.DateTimeField(null=True)

    class Meta:
        managed = False          # Django won't create, change or drop this table
        db_table = "core_investment"
```

With `managed = False` the old app keeps owning the schema, and the new code just reads and writes the same rows. There was never a question of which copy was right, because there was only one copy.

The cost is that you inherit every odd column name and table split from seven years of changes. I hid those behind cleaner models and APIs where I could, and only changed the tables themselves slowly, because the old app had to keep working after every change.

## Step 1: new frontends on the old API

The first thing people saw was a new admin app, still talking to the old backend. It lived on its own domain, with the old version still up on another, and people could use whichever they liked. Most of the team is French, so I also made sure numbers were formatted the way they expect. Over a few months fewer and fewer people opened the old one, until nobody did. That got users a better interface months earlier, and it meant I learned what every screen really needed by rebuilding it, not by reading old code. When the new backend was ready, the frontends only needed a different base URL.

## Step 2: a new backend on the same tables

Then I built the new backend underneath. Over the year the schema went from 154 tables to 101. For example, four overlapping legacy tables about who is connected to whom became one relationship model. Every one of those changes was a migration that the old app had to survive, since both were running at the same time.

## Step 3: check the numbers before anything switches

For money, "it looks right" isn't good enough. Before any part moved over, a small script ran the same calculations through both systems and listed the differences: portfolio KPIs, valuations, investor positions.

```python
def check_parity(metric: str, ids: list[int]) -> list[Mismatch]:
    mismatches = []
    for pk in ids:
        old = legacy_client.get_metric(metric, pk)   # old API
        new = compute_metric(metric, pk)              # new backend, same database
        if not close_enough(old, new):
            mismatches.append(Mismatch(metric, pk, old, new))
    return mismatches
```

There's nothing clever in it. It was useful because we ran it all the time. We got to 111 of 112 KPIs matching, and the last one was a change we made on purpose and wrote down before the switch.

## Step 4: switch one app at a time

The admin app went first, because its users were the internal team and would tell me quickly if something looked off. The investor app followed about ten days later. Each switch was mostly a config change, and going back would have been the same change in reverse.

Two small things kept investors from noticing much. We kept the existing password hashes, which Django already knew how to check, so nobody had to reset a password. And we told people in advance that they'd need to log in again once, because the login tokens changed format.

## Step 5: move, then switch off

Only after both apps were running on the new backend did I touch hosting. Moving from MySQL to Postgres was its own step, kept separate from any code changes. I wrote a migration script that could safely be run more than once, practised it on copies of production until it was dull, and then ran it for real once. After that the old AWS setup was switched off, and hosting costs dropped by about 95%.

## How two people managed it

A lot of the typing was done by coding agents, which only works with some structure around it. Every bigger change started as a written spec and a step-by-step plan. About 4,000 tests ran on every pull request. Each pull request got its own preview environment with a copy of production data, so reviewing meant clicking a link. And nothing merged without an automated review on top of ours.

## What I'd do differently

I'd write the parity script on day one, against the old API alone. It would have doubled as a description of what "correct" meant before I started changing anything.

I'd also turn the switch-over checklist into a script with a dry-run mode. The switches went fine, but the checklist lived in a document, and the practice runs and the real run should have been the same command.
